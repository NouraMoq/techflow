# نطاق الحد الأدنى للمنتج القابل للتسويق (MVP Scope) — «صانع المحتوى»

> **الشركة:** نوفاميتريكس | NovaMetrics — «من الفكرة إلى التأثير»
> **إصدار الوثيقة:** 1.0 (اختبار سوق) — **التاريخ:** 2026-07-18
> **مرجع:** وثيقة متطلبات المنتج (PRD) — `product-requirements-document-ar.md`

---

## 1. الغرض والمبدأ التوجيهي

هدف الـ MVP هو إثبات القيمة الأساسية للمنتج: نقل المحتوى **«من الفكرة إلى التأثير»** ضمن مسار واحد محوكم، بأقل نطاق كافٍ لاختبار السوق مع عملاء حقيقيين — دون بناء كل الوحدات المتقدمة.

**مبادئ اختيار النطاق:**
1. **إثبات المسار الأساسي أولاً:** فكرة ← سيناريو ← إنتاج ← موافقة ← نشر ← تحليل.
2. **Multi-Tenant من اليوم الأول:** العزل ليس ميزة مؤجّلة بل أساس معماري.
3. **لا تكاملات وهمية مقنّعة:** يُستخدم Mock Provider بوضوح، ولا يُدّعى نجاح نشر قبل تأكيد رسمي.
4. **عربي أولاً / RTL كامل** منذ أول شاشة.
5. **تأجيل ما لا يثبت القيمة الأساسية** إلى المرحلتين 2 و3 بمبرر واضح.

## 2. ما هو داخل الـ MVP

فيما يلي عناصر الـ MVP، ولكل عنصر: **المبرر** ومعايير القبول (**Acceptance Criteria — AC**).

### 2.1 التسجيل والدخول (Auth)
- **المبرر:** بوابة الوصول الآمن وأساس ربط المستخدم بالمستأجر والدور.
- **AC:**
  - يمكن للمستخدم التسجيل وتسجيل الدخول عبر Auth.js.
  - يُربط كل مستخدم بمستأجر ودور (RBAC) عند الدخول.
  - تُرفض محاولات الوصول غير المصادَق عليها للموارد المحمية.

### 2.2 تعدد المستأجرين (Multi-Tenancy)
- **المبرر:** شرط أساسي لنموذجي الخدمة المُدارة والوكالات، ويصعب إضافته لاحقاً.
- **AC:**
  - كل سجل حسّاس يحمل `tenantId`.
  - لا يستطيع مستخدم مستأجر رؤية بيانات مستأجر آخر (اختبار عزل يثبت ذلك).
  - يُطبَّق حذف ناعم (Soft Delete) ومعلومات تدقيق على العمليات الحسّاسة.

### 2.3 ملف صانع المحتوى (Creator Profile)
- **المبرر:** الكيان المركزي الذي ترتبط به بقية الوحدات.
- **AC:**
  - يمكن إنشاء/تعديل ملف صانع محتوى ضمن المستأجر.
  - يظهر الملف كمرجع في الاستراتيجية والأفكار والمشاريع.

### 2.4 الاستراتيجية (Strategy)
- **المبرر:** الهدف الأول — بناء استراتيجية واضحة تغذّي كل شيء.
- **AC:**
  - يمكن توثيق الرسالة، الجمهور، نبرة الصوت، الأهداف.
  - تُعرض الاستراتيجية للأدوار المصرّح لها وتُستخدم مرجعاً.

### 2.5 أعمدة المحتوى (Content Pillars)
- **المبرر:** يربط المحتوى بالاستراتيجية ويتيح قياس التوازن لاحقاً.
- **AC:**
  - يمكن تعريف أعمدة محتوى بنِسَب مستهدفة.
  - يمكن ربط الأفكار والسيناريوهات بعمود.

### 2.6 بنك الأفكار (Idea Bank)
- **المبرر:** بداية المسار الأساسي؛ يقلّل العشوائية.
- **AC:**
  - يمكن إنشاء فكرة بحالة ووسوم وربط بعمود.
  - يمكن تصفية الأفكار حسب الحالة/العمود.
  - يمكن تحويل فكرة إلى سيناريو.

### 2.7 السيناريوهات (Scripts)
- **المبرر:** الحلقة بين الفكرة والإنتاج.
- **AC:**
  - يمكن إنشاء سيناريو من فكرة، بإصدارات.
  - يمر السيناريو بحالات (مسودة، قيد المراجعة، معتمد).

### 2.8 سير عمل الإنتاج (Workflow)
- **المبرر:** يثبّت المسار الأساسي عبر مراحل واضحة.
- **AC:**
  - مراحل معرّفة (فكرة ← سيناريو ← تصوير ← مونتاج ← مراجعة ← اعتماد ← نشر).
  - يمكن تخصيص مسؤول لكل مرحلة وتتبّع الحالة.

### 2.9 التقويم التحريري (Editorial Calendar)
- **المبرر:** يحوّل الخطة إلى جدول قابل للتنفيذ (الهدف الثاني).
- **AC:**
  - عرض زمني للمحتوى المخطّط/المنشور.
  - فلترة حسب الحالة/العمود، ومزامنة مع المهام.

### 2.10 المهام (Tasks)
- **المبرر:** يوزّع العمل على الفريق ويقلّل الاعتماد على أدوات خارجية.
- **AC:**
  - إنشاء/تخصيص مهمة بموعد نهائي وحالة.
  - ربط المهمة بمشروع/جلسة تصوير/عنصر تقويم.

### 2.11 جلسات التصوير (Shoot Sessions)
- **المبرر:** جزء أساسي من الإنتاج المنظّم.
- **AC:**
  - جدولة جلسة بموقع وفريق وقائمة لقطات.
  - ربط الجلسة بالسيناريوهات والأصول الناتجة.

### 2.12 الملفات / مكتبة الأصول (Files / Assets)
- **المبرر:** لا إنتاج بلا إدارة أصول آمنة.
- **AC:**
  - رفع/تنزيل الأصول عبر Signed URLs على S3-compatible.
  - ضبط الوصول حسب الصلاحية، ووسوم وربط بالمشاريع.

### 2.13 الموافقات (Approvals)
- **المبرر:** الهدف الخامس — حَوكمة النشر.
- **AC:**
  - مسار اعتماد قبل النشر بسجل قرارات (اعتماد/رفض/طلب تعديل).
  - إمكانية التعليق وتسجيل هوية المعتمِد والوقت.

### 2.14 التحليلات التجريبية + الإدخال اليدوي (Pilot Analytics + Manual Input)
- **المبرر:** إثبات حلقة القياس قبل توفر التكامل الرسمي، دون بيانات وهمية مقنّعة.
- **AC:**
  - لوحات أداء أساسية عبر Recharts.
  - إدخال يدوي واضح المصدر للبيانات، مربوط بالمحتوى/العمود.

### 2.15 الحملات الأساسية (Basic Campaigns)
- **المبرر:** يمثّل بداية القيمة التجارية دون CRM كامل.
- **AC:**
  - إنشاء حملة وربطها بالمحتوى والتسليمات الأساسية.
  - تتبّع حالة الحملة على مستوى مبسّط.

### 2.16 العقود الأساسية (Basic Contracts)
- **المبرر:** حفظ الالتزامات التعاقدية المرتبطة بالحملات (هدف 8).
- **AC:**
  - إرفاق/تسجيل عقد وربطه بحملة.
  - تسجيل التسليمات والمواعيد النهائية الأساسية.

### 2.17 الباقات والاشتراك التجريبي (Plans & Trial Subscription)
- **المبرر:** ضروري لاختبار السوق ونماذج الأعمال الثلاثة.
- **AC:**
  - عرض الباقات (الانطلاقة/الاحتراف/النجم/الإدارة المتكاملة/الوكالات) وحدودها.
  - تفعيل اشتراك تجريبي وربطه بحدود الاستخدام.

### 2.18 لوحة نوفاميتريكس (NovaMetrics Console)
- **المبرر:** الهدف 12 — تمكين البيع كخدمة مُدارة.
- **AC:**
  - إدارة العملاء والاشتراكات مع عزل صارم.
  - رؤية مدير الحساب لعملائه فقط.

### 2.19 الواجهة العربية (Arabic UI / RTL)
- **المبرر:** مبدأ Arabic-first غير قابل للتأجيل.
- **AC:**
  - كل شاشات الـ MVP عربية بدعم RTL كامل.
  - المصطلحات التقنية بالإنجليزية عند الحاجة فقط.

### 2.20 بيانات أولية (Seed)
- **المبرر:** لتسريع العروض والاختبار وتجربة السوق.
- **AC:**
  - سكربت Seed ينشئ مستأجراً تجريبياً وأدواراً وبيانات نموذجية متسقة.

### 2.21 اختبارات أساسية (Basic Tests)
- **المبرر:** ضمان سلامة المسار الأساسي والعزل.
- **AC:**
  - اختبارات تغطّي المسار الأساسي وعزل المستأجرين والصلاحيات الحرجة.

## 3. ما يُؤجَّل للمرحلة 2

| العنصر | المبرر في التأجيل |
|-------|-------------------|
| التكامل الرسمي مع TikTok API | يتطلب اعتماداً رسمياً؛ الـ MVP يثبت المسار بالإدخال اليدوي وMock Provider. |
| التحليلات المحسّنة | تُبنى بعد توفر بيانات رسمية موثوقة. |
| التقارير المتقدمة | تُبنى فوق التحليلات المحسّنة. |
| مساعد الذكاء الاصطناعي الموسّع | قيمته تعتمد على نضج الاستراتيجية والبيانات؛ نبدأ محدوداً. |
| الفوترة الآلية والفواتير | الاشتراك التجريبي يكفي لاختبار السوق أولاً. |
| مركز الامتثال السعودي الكامل | يتطلب مراجعة قانونية معمّقة من مختص مرخّص. |
| مركز السمعة والأزمات | ليس ضمن المسار الأساسي لإثبات القيمة. |
| PWA والإشعارات المتقدمة | تحسينات تجربة تأتي بعد إثبات القيمة. |
| رادار الترندات (تكامل) | يبدأ يدوياً؛ التكامل لاحق. |

## 4. ما يُؤجَّل للمرحلة 3

| العنصر | المبرر في التأجيل |
|-------|-------------------|
| منصات إضافية (Instagram/YouTube/Snapchat) | تُضاف عبر Adapter Pattern بعد نضج TikTok. |
| ميزات الوكالات المتقدمة | تتطلب نضج نموذج متعدد المواهب أولاً. |
| White Label | إضافة تجارية متقدمة تعتمد على طلب السوق. |
| تطبيق جوّال أصلي (Mobile App) | يأتي بعد استقرار الويب. |
| Marketplace | يتطلب قاعدة مستخدمين ونضجاً تشغيلياً. |
| Benchmarking المجهول والتنبؤات والتوصيات المتقدمة | تحتاج بيانات كافية ونماذج ناضجة. |

## 5. معايير القبول العامة للـ MVP (Definition of Done)

- ينجز مستخدم حقيقي المسار الكامل: فكرة ← سيناريو ← إنتاج ← موافقة ← «نشر» (عبر Mock مع تصريح واضح) ← تحليل (إدخال يدوي).
- إثبات عزل المستأجرين عبر اختبار مخصّص.
- كل الشاشات عربية RTL دون كسور تخطيط.
- لا أسرار في الكود، والأصول عبر Signed URLs.
- لا يُدّعى نجاح نشر حقيقي في أي مكان بالواجهة.
- Seed واختبارات أساسية تعمل ضمن خط تكامل مستمر.
